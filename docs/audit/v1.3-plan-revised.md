# v1.3 Revised Plan — Post-Review Synthesis

Source: discussion 2026-07-08, building on the [original v1.3 roadmap](../ROADMAP.md#v1.3) and
codebase assessment.

## Principle shift

The original v1.3 plan placed the scaffold generator (A1) early. The revised principle:
**implementation validates the pattern; the generator codifies it after.** Build
notification as the last manual reference module, then graduate the scaffold into
a comprehensive CLI from 8 fully-tested examples rather than 2.

## What stays in markdown vs moves to GitHub Projects

**Markdown (historical record — stays in `docs/`):**
- `ROADMAP.md` — what shipped per version, why each feature exists
- `CHANGELOG.md` — per-release change log with operator notes
- `docs/audit/punch-list.md` — v1.1 pre-ship audit ledger (archival)
- `docs/audit/pr-NN-*.md` — per-PR scope documents (archival)
- `docs/audit/v1.3-plan-revised.md` — this document (decisions + rationale)

**GitHub Projects (active working board):**
- Phase 1-6 items as individual issues/notes
- Labels: `bug`, `feature`, `docs`, `debt`, `generator`, `queue`, `notification`
- Milestones: `v1.2.0` (wrap-up), `v1.3-phase-1`, `v1.3-phase-2`, etc.
- Custom fields: Tier (A-F), Risk (low/medium/high), Estimated hours
- Auto-links: PRs close issues automatically via `Closes #N`

## Generator — separate project or same repo?

**Same repo, same Go module.** Rationale:

1. The generator reads `go.mod` to determine the module path — it must live in the repo it generates for
2. Templates encode the canonical module pattern and **must co-evolve** with the modules themselves
3. Single import path for both runtime and tooling (`go run github.com/14mdzk/goscratch/cmd/goscratch`)
4. Users install alongside the project, not as a global tool

If the generator outgrows this scope (e.g., becomes a general Go project scaffolder
unrelated to goscratch), split it to its own repo then. Today it's firmly coupled
to this codebase.

## Key decisions captured

1. **Generator after implementation, not before.** 8 reference modules → encode patterns → generate. Doing it the other way codifies untested patterns.

2. **In-process worker is the default.** `queue.backend=goroutine` + `worker.in_process=true` out of the box. Zero-infrastructure dev experience. RabbitMQ and Redis are opt-in upgrades.

3. **Manual DI stays.** ADR-003's decision holds. The `app.go` wiring at ~487 lines / ~8 adapters is still readable and explicit. Revisit when adapter count crosses a threshold that makes manual wiring painful.

4. **GitHub Projects for execution, markdown for record.** The punch-list pattern served v1.0–v1.2 well, but manual checkbox sync across files is friction. GitHub Projects gives kanban, labels, milestones, auto-linking PRs. Markdown stays as the canonical "why."
