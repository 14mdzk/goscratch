## Cross-cutting requirements

- **Transaction boundary rule** (v1.3 Phase 3, item 9 — decision recorded in [#85](https://github.com/14mdzk/goscratch/issues/85)). Generated usecases must follow the adopted acceptance rule: wrap database work in `database.Transactor.WithTx` only when a single command's correctness spans more than one Postgres statement (a check-then-write, or ≥2 writes that must commit together). Never open a transaction for single-statement or cross-store work — Redis, object storage, and queue writes use ordering, idempotency, or compensation, and the feature doc records the failure mode. Audit entries are appended post-commit, best-effort, outside the transaction. The usecase template should carry this as comments so generated modules start compliant. Reference: `docs/architecture/patterns.md` → "Transaction Boundary" idiom + the dedicated transaction ADR (both land in v1.3 Phase 3 execution).
