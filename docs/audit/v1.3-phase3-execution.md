## 1. Transaction adoption — document-only, no `WithTx` in auth/storage/job

Verdict from [#85](https://github.com/14mdzk/goscratch/issues/85): **no `WithTx`
wiring in auth/storage/job.** No Postgres multi-statement write paths exist in
these modules; their only DB touch is the audit INSERT. Every multi-write path is
cross-store and already uses compensation or idempotency.

| Path | Writes (evidence) | Verdict |
|---|---|---|
| `auth.Login` | Redis dual-key `Set`x2 + compensating `Delete` (`auth_usecase.go:111,117,118`) | Document — cross-store, fail-closed |
| `auth.Refresh` | Redis `Delete`x2 -> `Set`x2 + compensation (`:167-168,186,189-190`) | Document — cross-store, fail-closed |
| `auth.Logout` | Redis `Delete`x2 (`:227-228`) | Document — idempotent |
| `auth.RevokeAllForUser` | Redis `SCAN`+`DEL` loop (`:237`, `redis.go:66-84`) | Document — idempotent; partial revocation surfaces an error |
| audit writes (auth/storage/job) | one `INSERT`, post-return (auth decorator `:37/:43/:60`, storage `:38/:55`, job `:34`) | Post-commit best-effort (intended) |
| `storage.Upload` | object-store write + audit (`storage_usecase.go:109,115`) | Document — no DB state; single object write; local adapter self-compensates |
| `storage.Delete` | object delete + audit (`:176-184`) | Document — idempotent (S3; local treats ENOENT as success) |
| `job.Dispatch` | queue publish + audit (`job_usecase.go:42,47`) | Document — single external write; ID-mismatch bug filed as #96 |
| worker handle/ack/retry | ack/re-publish, in-memory attempts (`worker.go:127,168-177,233`) | Document — broker-atomic claim; documented at-most-once window |
| audit cleanup | batched `DELETE` loop (`audit_cleanup_handler.go:61-84`) | Document — idempotent; bound tracked in #98 |

**Acceptance rule (adopted).** A usecase method wraps its database work in
`WithTx` when a single command's correctness depends on more than one statement
observing the same database state — a check-then-write (e.g. `user.Create`'s
exists->insert) or >=2 writes that must commit together. A single statement is
atomic alone — no transaction. Writes to stores other than Postgres (Redis,
object storage, queue) never ride the transaction: they use ordering,
idempotency, or compensation, with the failure mode documented in the feature
doc.

**Audit decorator semantics — confirmed intended.** Audit rows are appended
after commit, best-effort, on a separate pool connection — outside any failed
transaction. Failure-path auditing is explicit today only for auth
(`classifyLoginFailure` — sanitized categories, never raw error strings). Root
causes live in logs/metrics; audit rows carry outcome categories.

**Atomic in-tx audit is deferred to v1.4** (map Out of scope + ROADMAP
prospect): tx-aware `Transactor` nesting (savepoints) + tx-ownership rework. The
mechanism (in-tx insert vs outbox+relay) is reserved for that decision and gets
its own ADR there — not here.

Follow-ons filed from the audit: #96 (bug — dispatch audit ID != queued
message ID), #97 (debt — Redis dual-key failure windows), #98 (debt —
audit-cleanup loop bound); v1.3 Tier E5 (mutation failure-entry coverage +
audit-INSERT failures get logged instead of silently dropped, no schema change).
A1 scope updated so the generator encodes the rule: PR #99.

## 2. Role-write atomicity — per-call atomicity + document, duplicates -> 409

Verdict from [#91](https://github.com/14mdzk/goscratch/issues/91): **accept
per-call atomicity + document.** Phase 3 item 8's premise — "role assignment
touches multiple Casbin policy rows" — does not match the code: every
role-module write path is exactly one Casbin mutation -> one SQL statement
(`role_usecase.go` — AssignRole `:44`, RemoveRole `:66`, permission variants
`:121/:134/:207/:215`). The app `Transactor` (pgxpool-bound) cannot reach the
Casbin adapter's separate `*sql.DB` (`casbin.go:93`, `app.go:191`), and
sql-adapter v1.2.1 implements no `persist.TransactionalAdapter`, so Casbin v3
transactions are unavailable without a custom adapter. Item 8 resolves to
**document-only + duplicate-surface fix (409)** — no transaction
infrastructure, consistent with the §1 acceptance rule (`WithTx` only when one
command spans >=2 Postgres statements).

- **Approach — accept + document, no new infrastructure.** Keep the
  one-mutation-per-operation discipline; the `casbin_rules` UNIQUE index
  (`migrations/000003_casbin_rules.up.sql:16`) makes races loud, never
  corrupting. Standing rule: any future operation batching >=2 mutations uses
  Casbin batch calls (`AddPolicies`/`RemovePolicies` — already atomic per call
  via sql-adapter's `execTxSQL`). Cross-call transactions (custom
  `TransactionalAdapter`) and compensation logic are deferred post-v1.3; revisit
  only if a logical operation ever spans separate mutations **plus** post-commit
  side effects (map Out of scope).
- **Concurrent duplicate -> 409.** Check-then-write races on assign/add-permission
  paths currently surface as generic 500s (the racing INSERT hits the unique
  index). Detect SQLSTATE `23505` in the adapter (`errors.As` on
  `*pgconn.PgError`), surface an already-exists sentinel through
  `port.Authorizer` (sentinel lives in `port` so the usecase keeps its
  dependency direction: usecase -> port, never usecase -> adapter), map to
  `apperr.Conflictf` -> 409. Retry semantics: retrying a committed-but-errored
  write lands on a no-op, 409, or 404 — never corruption.
- **Cache invalidated on every mutation attempt, success and error.** The six
  mutation methods in `casbin.go` (`:278-377`) currently gate invalidation on
  `err == nil`, but a returned error cannot be told apart from a committed
  write (Casbin v3.10 returns watcher-notify errors *after* persist + model
  commit — `internal_api.go:378-401`; post-persist role-link/constraint
  failures can also error after state changed). Invalidation is idempotent and
  cheap; the dangerous direction (skipped invalidation after a committed revoke)
  is closed.
- **Watcher propagation stays best-effort; convergence bound = 5-minute backstop
  reload** (default, currently fixed — `app.go` passes only `DatabaseURL`). No
  reload-on-error, no retry/outbox for watch events. Rare mid-call model<->DB
  divergence stays the backstop's job — documented, not engineered around.

Operator-facing behavior (lands in `docs/features/role-management.md` "Failure
behavior & retries" with the execution PR): per-operation single-row atomicity;
concurrent duplicate -> 409; "an error response may accompany a committed
write"; retry guidance; 5-minute convergence bound.

## 3. Enforcer concurrency — swap to `casbin.NewSyncedEnforcer`

Verdict from [Issue #101](https://github.com/14mdzk/goscratch/issues/101):
swap the shared enforcer to **`casbin.NewSyncedEnforcer`** (option a).

- **Mechanism:** field type `Adapter.enforcer` becomes
  `*casbin.SyncedEnforcer`, constructed via `casbin.NewSyncedEnforcer(m,
  adapter)` — same call shape, ~2-line change. Verified against casbin v3.10.0
  source: SyncedEnforcer overrides with locking every method the adapter
  touches (`Enforce`, `LoadPolicy`, `SetWatcher`, all `Add/RemovePolicy` +
  grouping variants, `GetPolicy`/`GetGroupingPolicy`, `GetRolesForUser`,
  `GetUsersForRole`, `HasRoleForUser`, `GetPermissionsForUser`,
  `GetImplicitPermissionsForUser`, `SavePolicy`). No adapter call-site changes
  signature. Adapter-level mutex (option b) rejected: it would duplicate the
  upstream-tested wrapper and every future call site would need to remember the
  lock. Document-only (option c) rejected: race proven reachable (below).
- **Race evidence:** minimal `-race` repro (8 goroutines x Enforce + AddPolicy +
  GetPolicy, same model text as production) reports `WARNING: DATA RACE` in
  `model.Model.AddPolicy` via `addPolicyWithoutNotify` — the exact path
  production mutations take while request-path `Enforce` runs. Repro kept as
  scratch (`/tmp/enforcer_race_repro.go`), not committed.
- **Watchers must stay async.** Re-entrancy checked: watcher callbacks fire on
  the subscriber goroutine (async Redis pub/sub), never synchronously inside a
  lock-holding call, so the non-reentrant RWMutex cannot deadlock. Standing
  constraint: watcher implementations must stay async (true of `RedisWatcher`).
- **Perf:** reads share RLock (no serialization among readers); hot path stays
  fronted by the already-thread-safe decision cache; writes (admin mutations,
  5-min backstop `LoadPolicy`) serialize briefly — acceptable at RBAC mutation
  rates.
- **Acceptance for the execution PR:** must ship a concurrency regression test
  (concurrent `Enforce` + mutation under `-race`, in-memory or miniredis-backed)
  as its proof; the test stays with the project beside the adapter tests.
- **No standalone ADR** — rationale folds into this bundle (cheap to reverse, no
  new domain term). Fog item D2 (`RedisWatcher` wiring in `app.go`) is unblocked
  by this decision and needs no extra guard beyond the async-callback
  constraint; D2/D3 remain fog until execution wires them.
