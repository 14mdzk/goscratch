## Origin

[Decide the queue backend spectrum](https://github.com/14mdzk/goscratch/issues/84) declared RabbitMQ first-class and made an unreachable durable backend fail boot. That raised the profile of three known correctness gaps — publisher reconnect, dead-lettering, retry backoff — and the scope decision surfaced a fourth: retries live in process memory, not in the broker. [#94](https://github.com/14mdzk/goscratch/issues/94) settled what v1.3 does with all four; this document is the execution scope. Decisions only below — nothing here re-opens them.

## Design (decided)

### 1. Publisher-side reconnect

Today only consumer channels reconnect (`reconnectConsumer`, `internal/adapter/queue/rabbitmq.go:305-331`); the cached publisher channel is replaced only as a side effect of a *consumer* reconnect, so an API-only process keeps a dead publisher after a broker bounce and dispatch returns `INTERNAL_ERROR` 500s until restart. The file comment at `rabbitmq.go:16-25` claims connection-level `NotifyClose` handling that does not exist.

- Register `NotifyClose` on the connection (`amqpConnection` already declares it, `rabbitmq.go:39`) and mark the cached publisher channel dead when it fires — under `pubMu`, next to `closed`.
- On a publish that fails with a channel/connection-closed error, redial **once** through the existing `redial` path (bounded by `MaxReconnectTries` / `ReconnectBaseDelay` / `ReconnectMaxDelay`) and retry the publish **once**; if the retry also fails, surface the original error unchanged (the usecase still maps to a 500).
- No new config keys: the reconnect knobs stay code constants.
- Correct the file comment to describe what the adapter actually does.

### 2. Held retry — the broker owns the job across the backoff

Today the worker ACKs first and republishes from a goroutine after the delay (`internal/worker/worker.go:177`, `retryJob:196-236`): a restart/OOM/redeploy mid-backoff loses the job.

- On a handler error with retries left, `handleMessage` neither returns nil nor an error immediately: it waits out the backoff **in the handler's own goroutine** (context-aware `time.Timer` + `select` on the worker context), republishes the job with the incremented attempt, then returns nil → the adapter ACKs.
- The wait uses the worker context, not the per-handler 5-minute timeout context.
- On `ctx.Done()` during the wait: do not republish; return an error so the adapter `Nack(false, true)`s (`rabbitmq.go:294`) and the broker redelivers. The payload's `attempts` was never republished, so the next run re-increments to the same number — no double-count, and the port's `Nack(requeue=true)` path becomes real in production (it is unreachable today).
- `retryJob`'s goroutine and `wg` tracking disappear for this path; shutdown no longer waits out a backoff.
- Port comment update in `internal/port/queue.go`: a handler may block for the length of a retry backoff, and adapters must not settle the delivery until the handler returns.
- Backend parity: the port contract already expresses this (`nil` = ack, `error` = reject/requeue). `GoroutineQueue` (Phase 4 item 10) inherits the shape but not the durability — process-local, documented best-effort.

### 3. Backoff — capped exponential + jitter

`attempts²` seconds, uncapped, unjittered (`worker.go:196-197`), while the docs say "exponential" (`docs/features/background-jobs.md:5,83`; `README.md:49`; CHANGELOG wording).

- `delay = min(1s × 2^(attempts-1), 60s)` × jitter (random factor in `[0.5, 1.0)`), constants inline — no new config keys.
- The 60s cap is chosen with §2 in mind: under hold-the-delivery it is the bound on how long one delivery can occupy a consumer channel.
- Correct the docs wherever "exponential" appears next to an `attempts^2` formula.

### 4. Dead-letter queue — no terminal path drops silently

Exhausted retries (`worker.go:168-177`), malformed payloads (`:120-124`) and unhandled job types (`:141-147`) are ACK-dropped today; no DLX/DLQ exists in the repo.

- Every terminal path publishes the payload to a derived dead-letter queue — `worker.queue_name + ".dlq"` (`jobs` → `jobs.dlq`) — declared durable at startup next to the main queue the worker already declares, then ACKs.
- The parked payload is the original bytes verbatim, so re-publishing to the main queue replays the job. Reason metadata (`reason`, `job_type`, `attempts`, `last_error`) is emitted in the worker's structured error log at park time. If implementation prefers embedding the reason in the parked message, the original job JSON must stay recoverable unmodified (e.g. as an envelope field) — replayability is the constraint.
- Park failure → requeue (never ACK a message that was not parked); **except** undecodable payloads, which fall back to ACK + error log after a failed park — a requeue loop on an undecodable payload has no attempt counter to stop it (poison-message guard).
- No new config keys, no redrive tooling in v1.3: operators inspect and replay via the broker UI; `docs/RUNBOOK.md` gets an incident note.
- `GoroutineQueue` parks into an unconsumed channel — best-effort, documented in that backend's own section.

## Explicitly Out of Scope

- **Concurrent delivery dispatch** in the RabbitMQ consumer (goroutine-per-delivery + guarded ack) — [#103](https://github.com/14mdzk/goscratch/issues/103), post-v1.3, ROADMAP v1.4 prospect. v1.3 accepts serial dispatch and documents the levers.
- **Broker-native retries** — DLX/`x-dead-letter-exchange`, retry queues with per-message TTL, `x-death` accounting. Retry stays worker-owned so the `goroutine` default and the future `redis` tier keep one code path.
- **DLQ redrive tooling** (API endpoint, CLI, metrics/dashboards for DLQ depth).
- **Config keys** for reconnect/retry/backoff — constants only in v1.3.
- Publisher-side connection pooling beyond the single cached channel.
- **DLQ durability on the `goroutine` backend** — best-effort by construction, documented only.
- Redis queue tier (`RedisQueue`), the Phase 4 spectrum config work, CLI, OpenAPI, geo, Casbin, notification code.
