# v1.3 Tier F2 — k6 Load Baseline Harness

**Branch:** `feat/f2-k6-baseline-harness`
**Roadmap reference:** Tier F, row F2 (k6 script targeting `/auth/login`, `/files/upload`, `/files/{id}`; baseline req/s + p99 under sliding-window rate-limit).

## Design (decided)

### 1. One script, paced under the limiters (`k6/baseline.js`)

- `setup()`: single `POST /auth/login` (seeded `admin@example.com` / `admin123`
  via `make seed-fresh`) → bearer token shared by all VUs. One login total:
  the auth limiter (20 req / 5 min / IP, hardcoded in `auth/module.go`) makes
  per-iteration login impossible, and a 2-minute run fits the 15-minute
  access-token TTL.
- VU loop (self-cleaning CRUD): `POST /files/upload` (multipart `file` field,
  `directory=k6-baseline`, 10 KB random payload) → `GET /files/download/<path>`
  from the 201 response → `DELETE /files/<path>`. Three requests per iteration.
- Pace: 4 VUs × 1 iter per 10 s (`sleep(10)`) = 24 iter/min = 72 req/min
  aggregate, under the default global limiter (100 req / 1 min from
  `.env.example`). Expected 429 rate at this pace: zero — any 429 fails the
  run and means the pace math or the limiter config drifted. No early
  returns: every VU path ends at the single paced sleep, so a failing
  endpoint slows down instead of hot-spinning into a 429 storm.
- Duration 2 min (`stages`: 20 s ramp, 80 s steady, 20 s ramp-down).
- Thresholds (the floor): `http_req_failed < 1%`, `http_req_duration p99 < 1500ms`
  (local-dev floor, generous on purpose — first benchmark sets it; tighten
  from data, not ambition). Login duration reported as a custom Trend
  (`login_duration`), not thresholded (single sample per run).

### 2. Runner surface

- `make k6-baseline` → `k6 run k6/baseline.js` (base URL via `BASE_URL` env,
  default `http://localhost:3000`; creds via `K6_EMAIL` / `K6_PASSWORD`).
- `k6/README.md`: prerequisites (compose pg+redis, `migrate-up`, `seed`,
  running API), the exact command sequence, how to read the output
  (req/s + p99 + login Trend), and the recorded baseline table.
- No CI job: k6 needs a live seeded stack; CI has neither. The harness is a
  local/operator tool (same reason pg integration is local-gated).

### 3. Verification

- Run the full sequence locally (compose → migrate → seed → API → k6) and
  record req/s + p99 + login ms in `k6/README.md`.
- `k6 check`-style dry validation: `k6 run --vus 1 --iterations 1` smoke run
  against the live stack before the full baseline.

## Out of scope

- Stress / spike / soak profiles (baseline only; add scenarios later).
- Authenticated multi-user shapes (one shared admin token by design — see above).
- Per-endpoint limiter probing (would intentionally trip 429s; separate exercise).
- CI integration (no live stack in CI).
