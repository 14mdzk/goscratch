# v1.3 Tier E3 — `JWT_SECRET` Overlap Rotation

**Branch:** `feat/e3-jwt-overlap-rotation`
**Roadmap reference:** Tier E, row E3 (`JWT_SECRET` rotation support — accept both previous + current during a `JWT_SECRET_PREVIOUS` overlap window). RUNBOOK §1 documents the no-overlap rotation as a known sharp edge.

## Design (decided)

### 1. New config key, verify-both / sign-current

- `config.JWTConfig` gains `PreviousSecret string` (`previous_secret`, `JWT_SECRET_PREVIOUS`). Empty = rotation disabled (today's behavior).
- Verification (`parseToken`, the single choke point behind all six modules' `middleware.Auth`): try the current secret; on failure try the previous secret; if both fail return the **current-secret error** so expired-vs-invalid messaging stays accurate. Signing (`generateAccessToken`) always uses the current secret, so refreshes migrate sessions onto the new key automatically.
- Validation: a non-empty previous secret must satisfy the same rules as the main secret (≥32 bytes, not the committed placeholder) — fail boot otherwise. Equal-to-current is tolerated (behaves as unset).

### 2. Plumbing

- `middleware.AuthConfig` gains `JWTPreviousSecret`; `DefaultAuthConfig(current, previous string)`.
- The five modules that plumb a bare `jwtSecret string` (user, role, storage, sse, job) gain a `jwtPreviousSecret` field + constructor param; call sites (`app.go`, `testutil/testapp.go`) pass `cfg.JWT.PreviousSecret`. The auth module already holds the full `JWTConfig` and reads the field directly. No module `_test.go` constructs these modules, so test fallout is nil.
- Out of scope: touching refresh-token storage (opaque tokens, secret-independent) and access-token TTL semantics.

### 3. Operator procedure (RUNBOOK §1 rewrite)

Set `JWT_SECRET_PREVIOUS` = old value, `JWT_SECRET` = new value, roll: old-signed tokens keep validating while new logins mint new-signed tokens. Verify (old token → 200, new login → works), then clear `JWT_SECRET_PREVIOUS` and roll again. Rollback = restore the old pair.

## Out of scope

- Refresh-token invalidation on rotation (secret-independent; §2 covers explicit cleanup).
- Key versioning / `kid` headers (one previous key is enough for a rolling restart).
