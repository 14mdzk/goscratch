# v1.3 Issue #97 — Auth Dual-Key Hardening (Refresh Rotation, RevokeAllForUser)

**Branch:** `fix/97-auth-dual-key-lua-sweep`
**Map ticket:** [#97 — Auth: harden Redis dual-key failure windows](https://github.com/14mdzk/goscratch/issues/97) on the v1.3 Route Map (#83).
**Status note:** the issue states current semantics are fail-closed and intentional — this tracks hardening options, not a defect. The decisions below pick the options worth taking; the rest are explicitly declined with rationale.

## Findings (confirmed on current main)

- `authUseCase.Refresh` (`internal/module/auth/usecase/auth_usecase.go`): deletes the old lookup + index keys, then writes the new pair; mid-write failure compensated best-effort. Any failure returns 401/500 — the client re-logs-in. Fail-closed.
- `userUseCase.ChangePassword` (`internal/module/user/usecase/user_usecase.go`): updates the password hash first, then calls `RevokeAllForUser`; a revocation error is propagated (`password updated but refresh token revocation failed`), so the operator/user sees it and retries. Fail-closed.
- `RedisCache.DeleteByPrefix` (`internal/adapter/cache/redis.go`): client-side SCAN + DEL loop. A mid-loop transport failure returns an error (caller retries, idempotent) — but the keys deleted before the failure stay deleted while the rest survive: a *partial revocation* that only a retry heals.

## Design (decided)

### 1. Refresh rotation: keep delete-old-then-write-new (no code change)

Write-new-then-delete-old would shrink the forced-relogin window but replaces it with a systematic double-valid window: a crash between the write and the delete leaves the old and new refresh tokens simultaneously valid until TTL. The current order's worst case is a forced re-login (safe, annoying); the alternative's worst case is two live sessions (unsafe). Keep the order; add a one-line rationale comment at the delete site so nobody "optimizes" it later.

### 2. DeleteByPrefix: single Lua sweep (the code change)

Replace the client-side SCAN + DEL loop with one `EVAL`: the script loops `SCAN` server-side, `DEL`s each batch, returns the deleted count. Server-side execution is atomic — no other client interleaves — so a transport failure can no longer leave a partial revocation: the call either fully applied or fully failed. On script error, return the error unchanged (fail-closed; `ChangePassword` propagates, retry heals).

- No `port.Cache` signature change: `DeleteByPrefix(ctx, prefix) error` stays.
- No new config keys, no retry wrapper: atomicity removes the partial state that retry would heal, and go-redis already owns reconnects. A retry loop around an atomic op adds nothing.
- Batch `COUNT 100` inside the script; per-user session counts are small, so the script holds the server briefly.

### 3. Declined: metrics on partial revocation

Partial revocation stops existing with (2); instrumenting a state that can no longer occur is dead code. The completion/error return remains the signal.

## Out of scope

- Generation counters / version stamps for logins racing a revocation (inherent race, needs a design of its own).
- NoOp-cache behavior (`DeleteByPrefix` still returns `ErrCacheUnavailable`; `ChangePassword` still surfaces it).
- Refresh metrics or rotation retry/backoff.
